# Inventory: what moves into suwgate

Every guard and every step of the two gates suwgate replaces, and where each one goes. Sources:

- **tpl** = the template solid-dotnet-app-tpl: Myapp.Gate/ (the guards as xUnit tests, criteria.json, layers.json, scripts/),
  scripts/.internal/, .githooks/, .claude/, and the database tests in Myapp.Server.Tests/.
- **kit** = the library suwfrontkit (formerly suwfrontstyle; the npm package @maniumek/suwfrontkit): gate/guards/, gate/scripts/,
  eslint.config.js, .githooks/, .claude/.

Source paths are written as plain text, not as links: they live in those repositories, not here (a docs-paths guard must not read
them as paths of suwgate; work package B gives this file an exception with that reason when it moves that guard).

Targets:

- **CLI guard**: a repository guard of the CLI (`src/guards/<package>/`, contract in [architecture.md](architecture.md)).
- **step**: a step of a profile (`src/profiles/`), or of every repository.
- **Suwgate.Architecture** / **Suwgate.Database**: a .NET guard (`IGuard`), called from the application's xUnit tests.
- **core**: already done by the gate itself in this round.
- **stays**: stays in the application or the kit, because it is about that repository only; it runs there through `steps.add`
  or as its own test. The runtime halves of what is checked here (generating a contract, the dev scripts) go to the kits:
  suwfrontkit for the front end, suwbackkit (the future backend kit) for the backend.

The letter in brackets is the work package at the end of this file. The proposed guard ids are binding once a repository names
them in `suwgate.yml`; a package may refine an id before it ships.

## Work packages for parallel agents

Five packages that touch disjoint folders. Each package adds its guards to the array of its own `src/guards/<package>/index.ts`
(the five barrels exist already, so nobody edits `src/guards/index.ts`) and its steps to its own files in `src/profiles/`.

Shared rules for all five:

- `src/gate/` (the core), `schema/` and `dotnet/Suwgate.Architecture/Verification/` (the .NET contract) change only through the
  coordinator: a package that needs a new field asks, with the reason, instead of changing it.
- A new guard that suwgate itself fails is fixed in suwgate, or gets an exception with its reason in `suwgate.yml`. `suwgate.yml`
  is protected by the edit hook: the agent gives the owner the exact lines (append-only, one block per package, so two packages
  do not conflict).
- No new npm dependency without the coordinator, who merges `pnpm-lock.yaml` once; .NET packages go into `Directory.Packages.props`,
  which package D owns: E asks D.
- Every guard ships with a test of its rules (examples that pass and that fail, as the sources' InlineData and `it.each` do) and
  a finding message that states the fix. A guard id is kebab-case; a .NET guard's id starts with `architecture/` or `database/`.
- Each package runs `node src/cli.ts check` once, at its end, over the whole repository.
